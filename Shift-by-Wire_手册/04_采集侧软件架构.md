# 第 4 章：采集侧软件架构（S32K144）

## 7 个任务与优先级

| 任务 | 函数 | 周期 | 优先级 | 栈 | 职责 |
|------|------|------|--------|-----|------|
| Heart | `vTask_Heartbeat` | 500ms | 2 | 256 | 蓝灯翻转 |
| ADC | `vTask_ADC_Sample` | 10ms | 3 | 384 | 4 路 ADC + 每 100ms 推车辆模型 |
| Gear | `vTask_Gear_Logic` | 10ms | 3 | 512 | 输入映射 → 状态机一步 |
| CANTx | `vTask_CAN_Tx` | 10ms | 3 | 384 | 发 0x180 |
| CANRx | `vTask_CAN_Rx` | 10ms | **4** | 256 | 收 0x280 + 500ms 超时 |
| Btns | `vTask_Buttons` | 10ms | 2 | 256 | 双键消抖 |
| Debug | `vTask_Debug` | 100ms | 2 | 512 | HMI 屏幕刷新 + 演示面板 |

**为什么 CANRx 优先级最高？** 因为它做的是"把中断已经收到的东西搬进软件计数器"。如果它被 ADC 或 Debug 阻塞，`timeoutCnt` 的更新节奏就和真实帧到达节奏脱钩，500ms 超时判定会失真。它本身只读队列、更新两个 `volatile` 变量，执行时间 <20µs，给最高优先级不会饿死别人。

**为什么 ADC/Gear/CANTx 同为 3？** 它们都是 10ms 硬周期且互相依赖（ADC 出的摇杆值 → Gear 用；Gear 出的档位 → CANTx 用）。同优先级 + 时间片轮转，实际执行顺序由 FreeRTOS 的 tick 到期顺序决定，但每轮都在 10ms 内完成，不需要更强的顺序保证。

## 任务间通信：裸 `volatile` 全局量

```c
volatile uint8_t  g_current_gear;   /* 状态机输出，CANTx 和 ADC(车辆模型) 都读 */
volatile uint8_t  g_comm_valid;     /* CANRx 写，Gear 读 */
volatile uint8_t  g_actual_gear;    /* CANRx 写 */
volatile uint16_t g_stick_x_raw, g_stick_y_raw;
volatile uint16_t g_stick_rest_x, g_stick_rest_y;
```

没有队列、没有信号量。理由：

- 全是**单写单读**的整数，Cortex-M4 对 `uint8`/`uint16` 的对齐读写是原子的。
- 换挡是 10ms 级控制，读到一个"上一拍的值"完全无害——下一拍就更新了。
- 用互斥量反而引入优先级反转风险（Debug 任务持锁被抢占）。

> 这是**有意为之的简化**，不是遗漏。如果将来加入 32 位以上结构体或跨任务缓冲区，必须改用队列。

## ADC 模块（`sbw_adc.c`，317 行）

### 四个通道

| 通道 | 变量 | 用途 | 配置结构体 |
|------|------|------|-----------|
| ADC0_SE2 | `adc_brake` | 刹车 0~100% | `peripherals_adc_config_1.h` |
| ADC0_SE3 | `adc_speed` | 油门 0~100% | 同上 |
| ADC0_SE10 | `adc_x` | 摇杆 X 原始值 | 同上 |
| ADC0_SE11 | `adc_y` | 摇杆 Y 原始值 | 同上 |

采样在 `ADC_SampleAll()` 里串行做：`ADC_DRV_ConfigChan(..., 0U, &chan)` → `while(!WaitConvDone)` → `ADC_DRV_GetChanResult`。10ms 一轮采 4 次，单次转换约 3µs，总耗时远小于周期。

### 踏板：死区 + 滑窗

```c
#define ADC_FILTER_WINDOW 8      /* 8 点滑动平均 */
#define ADC_DEAD_LOW      200    /* 低于 200 counts 视为 0% */
#define ADC_FULL_SCALE    4095
```

`ADC_RawToPercent()`：先 8 点滑窗去噪，再 `(avg - 200) * 100 / (4095 - 200)`，钳位到 0~100。

死区 200 不是拍脑袋：实测踏板静止时 ADC 读数在 30~120 之间跳动（电源纹波 + 电位器磨损），旧值 60 会让静止时油门显示 1~2%，而车辆模型里 2% 油门 = 持续加速 → "刹车关了车速拼命往上冲"（第 11 章坑 #2）。

### 摇杆：上电自校准 + 行程百分比 + 迟滞

**问题**：这个摇杆的机械中位对应 ADC 约 **2936**，不是 12 位中点 2048。如果用固定阈值（比如 <1200 → 1、>2800 → 2），**松手状态就已经落在 2 档**上——这正是"不解锁也能进 D / 一直跳 M"的根源。

**方案**：上电前 100 次采样（1 秒）取平均作为回中基准 `s_restX` / `s_restY`，之后所有判断都相对于这个基准：

```c
static uint8_t ADC_ToStickPos(uint16_t adc, uint16_t rest, uint8_t prev)
{
  uint16_t lo = (uint16_t)(rest - (uint32_t)rest * 95 / 100);        /* 2936 → 147 */
  uint16_t hi = (uint16_t)(rest + (uint32_t)(4095 - rest) * 95 / 100); /* 2936 → 4037 */

  if (prev == 2) lo += 120;   /* 迟滞：当前在"后拉"，要回到更靠近中点才算松手 */
  if (prev == 1) hi -= 120;

  if (adc < lo) return 2;     /* 后拉 */
  if (adc > hi) return 1;     /* 前推 */
  return 0;                   /* 回中 */
}
```

**三个设计点**：

1. **按行程百分比而不是绝对值**：基准两侧的可用行程并不对称（一侧 2936、另一侧 4095-2936=1159），用 `rest ± (行程×95%)` 保证两侧触发点都在各自电气尽头的 95% 处。
2. **迟滞 120 counts**：防止推到边界附近时在 1/0 之间抖动。`prev` 决定往哪个方向收窄，形成"进得去、出不来"的迟滞环。
3. **校准期间强制输出 0**：`s_calCount < 100` 时 `g_stick_x = g_stick_y = 0`，避免上电瞬间误判成"摇杆推到底"。

> 已知局限：这个摇杆的电位器被过驱动（机械行程走到一半电位器就到电阻轨道尽头），导致"手感上还没推到底就已经触发"。功能上无影响（只用 0/1/2 三态），但根因是连杆比与电位器电气角度不匹配，硬件改法见第 11 章坑 #8。

## 按键模块（`sbw_buttons.c`，80 行）

```c
uint8_t BoardKeyIsPressed(GPIO_Type *base, uint8_t pin, uint8_t activeLevel);
uint8_t BoardKeyDebounced(GPIO_Type *base, uint8_t pin, uint8_t activeLevel, uint8_t idx);
```

- `activeLevel` 参数化：`!=0` 表示高有效。
- 消抖：连续 3 次采样（3×10ms = 30ms）一致才确认状态变化。
- 两键分别传 `BTN_P_ACTIVE_LEVEL`(0，低有效) 与 `BTN_UNLOCK_ACTIVE_LEVEL`(1，高有效)。

**为什么极性不写死**：项目里两个键硬件极性相反，如果函数内部硬编码 `!HAL_GPIO_ReadPin()`，改硬件或换板子就要动函数体。参数化后，极性成为头文件里的两个数字，`git diff` 一眼可见。

## HMI 模块（`sbw_hmi.c`，320 行）

### 发送

| 函数 | 发出的字节 | 用途 |
|------|-----------|------|
| `HMI_SendNumber("n0", 45)` | `n0=45` + `FF FF FF` | 数字控件 |
| `HMI_SendString("t0.txt", "D")` | `t0.txt="D"` + `FF FF FF` | 文本控件 |
| `HMI_SendFloat` | 格式化后同上 | 调试用 |

**三个 `0xFF` 是 Nextion 的指令结束符**，少了屏幕不执行。这是踩过的坑（屏幕不刷新但串口有波形）。

### 接收

256 字节环形缓冲 + 三态解析机（`DATA → FF1 → FF2`），帧长上限 64 字节。`HMI_Init()` 里在使能中断**之前**把 `LPUART1_RxTx_IRQn` 优先级设为 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`（=1）：

```c
NVIC_SetPriority(LPUART1_RxTx_IRQn, configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY);
```

**为什么必须先设优先级再使能**：FreeRTOS 的 `configASSERT` 在 `xQueueSendFromISR` 里检查"中断优先级数值不能小于 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`"。若先使能中断、ISR 在设优先级前触发，会直接断言失败进入 `configASSERT` 死循环。

## CAN 诊断三件套（`sbw_can.c`）

通信出问题时，最没用的信息是"CAN LOST"。本项目把控制器自身的错误状态读出来，直接投到屏幕上：

| 函数 | 读的寄存器 | 返回 |
|------|-----------|------|
| `CAN_GetBusState()` | `ESR1[5:4]` FLTCONF | 0=正常 1=错误被动 2=bus-off 3=未初始化 |
| `CAN_GetErrCounters(&tec, &rec)` | `ESR1[23:16]` / `ESR1[31:24]` | 发送错误计数 / 接收错误计数 |
| `CAN_GetErrFlags()` | `ESR1[15:10]` | bit0=STFERR bit1=FRMERR bit2=CRCERR bit3=ACKERR bit4=BIT0ERR bit5=BIT1ERR |

`rtos.c` 的 `Demo_Reason()` 把它翻译成人能读的一行：

| 显示 | 判据 | 说明 |
|------|------|------|
| `TX BITER` | BIT0/BIT1 置位 | 本板发送通道坏了 |
| `NO ACK` | ACKERR 置位 | 帧好的，没人应答 |
| `FORM ERR` | STF/FRM/CRC 置位 | 双方都能发但解不出（多为波特率不一致） |
| `BUSOFF` | FLTCONF == 2 | 已被踢出总线 |
| `NO PEER` | `TEC>0 && REC==0` | 自己在发、一帧没收到 |
| `SILENT` | `TEC==0 && REC==0` | 发送任务可能没跑 |

> **为什么 `REC` 这么关键**：只要对端发过任何一帧，`REC` 就会涨。`REC==0` 是"这条线上根本没有第二个节点在说话"的铁证——它把"对端没上电"和"对端活着但数据错"彻底分开了。这个判断在第 11 章坑 #13/#14 里救过场。

## 调度时序的实际表现

- 10ms 周期内：ADC 采样 ~15µs、状态机一步 ~5µs、CAN 发送（**非阻塞**，邮箱忙就跳过）~10µs、按键 ~2µs。总占用 <2%。
- 100ms 的 Debug 任务发 6 个数字 + 2 个文本 = 8 条 Nextion 指令，约 200 字节 @115200 ≈ 17ms。**这是全系统最长的单次阻塞**，所以它放在最低优先级 2，且 GP 优先级低于所有 10ms 任务（同为 2，靠时间片轮转，但 Heart 只翻转一个 IO，不阻塞）。
- 若将来屏幕刷新变慢（比如加波形），应把 HMI 发送改成"每 100ms 只发变化的控件"——`Demo_SendChanged()` 里的 `s_shadow[]` 阴影缓存就是为此设计的。
