# 第 8 章：故障安全与降级

## 四级防线

```
第 1 级：通信看门狗（G474 侧 500ms）—— 执行侧自己发现"指令没了"
第 2 级：通信看门狗（S32K 侧 2s）  —— 决策侧发现"执行侧没回话"
第 3 级：独立看门狗（G474 1.25s）  —— 执行侧软件跑飞时硬复位
第 4 级：独立看门狗（S32K 1.0s）   —— 决策侧软件跑飞时硬复位
```

四级的触发条件、时间尺度、动作都不同，**任何一级独立生效**。这是功能安全里"防御纵深"的最小可用形态。

> 注意第 1/2 级管的是"**沉默**"（对方不说话了），第 3/4 级管的是"**自己瘫了**"。两者之间还有一类"对方活着但在说错话"，由第 8.4 节的车速字节 + 重启检测负责。

## 第 1 级：G474 通信超时（500ms）

```c
#define CAN_RX_TIMEOUT_MS 500

if (now - g_can_rx_tick > CAN_RX_TIMEOUT_MS) {
  g_status |= STATUS_COMM_TIMEOUT;   /* 只置位 */
} else {
  g_status &= ~STATUS_COMM_TIMEOUT;
}
```

**动作：冻结。** 不改 CCR、不归位、不关 PWM，舵机保持在上一条指令的位置。

**剩下的隐患**：`g_comm_valid` 恢复后，G474 会继续执行**恢复瞬间收到的**那条指令。如果这期间 S32K 已经重启并回到 P，而车还在 D——G474 会在通信恢复的瞬间把舵机拉到 P。这是第 8.4 节要讨论的加固点。

## 第 2 级：S32K 通信超时（2s）

```c
#define COMM_TIMEOUT_ENABLE 1U   /* rtos.c:361，调试时置 0 可整体关掉 */

if (++timeoutCnt > 50U) {        /* 50 × 10ms = 500ms */
  g_comm_valid = 0;
}
```

收到 0x280 时 `g_comm_valid = 1; timeoutCnt = 0;`。

然后状态机里的 `comm_timeout_timer` 在 `valid==0` 时每步 +1，**>200 步（2s）** 进 FAULT。

**两级时间常数的选择**：
- 500ms 是 FreeRTOS 侧的"新鲜度检查"——10ms 周期发帧，500ms 等于连续丢 50 帧，肯定是真断了。
- 2s 是状态机侧的"降级判据"——10ms 周期下就是连丢 200 帧，偶发丢帧根本到不了；再往上加没有收益（60km/h 下每多 1s 就多开 16m，却换不来任何判据精度）。

## FAULT 状态的行为

```c
case GearShift_Stateflow_IN_FAULT:
  GearShift_Stateflow_Y.current_gear = 255U;   /* 非法档位码 */
  ...
  if (p_button && speed<5 && x_prev==0) → P
```

- 输出 255。G474 收到后**保持当前角度不动**、只置 `status.bit2`——执行侧绝不替决策侧做决定。
- 早期版本这里 255 会经 `GearToAngle()` 的 default 落到 72°（N），等于执行侧自己换挡；已改为"非法码拦截"。
- **唯一出口是"按 P 键 + 踩刹车 + 停稳 + 摇杆回中"**（模型 v1.24 起四项都在模型里），符合"故障后必须人工确认"的原则。
- 注意：如果通信本身断了，S32K 发的 255 根本到不了 G474。FAULT 状态的实际效果是**屏幕显示 F，同时停止发有效指令**。

## 第 3 级：IWDG

```
LSI 32kHz / 64 = 500Hz，Reload 625 → 1.25s
```

在主循环 `vTask_CAN_Tx` 里 `HAL_IWDG_Refresh(&hiwdg)`。**喂狗与"能发出帧"绑定**：如果 CAN 发送阻塞、调度器卡死、CAN 控制器进 bus-off 死等，狗都喂不上。

> 注意：`AutoRetransmission = DISABLE` 使得总线错误不会导致发送死等，这一点上 IWDG 是最后一道保险。

## 第 4 级：S32K144 WDOG（1.0s）

```
时钟 LPO 128kHz → 256 分频 → 500Hz 计数，TOVAL 500 → 1.0 s
喂狗：vTask_Heartbeat（500ms）确认五个周期任务都活着，才写 0xB480A602
```

**关键设计：喂狗与否，看的是"任务在不在跑"，不是"CAN 通不通"。**

```c
/* rtos.c：每个周期任务每跑一圈给自增一次 */
static volatile uint32_t s_aliveAdc, s_aliveGear, s_aliveTx, s_aliveRx, s_aliveBtn;

/* vTask_Heartbeat：五个都推进过，才喂 */
if ( (s_aliveAdc != lastAdc) && (s_aliveGear != lastGear) &&
     (s_aliveTx  != lastTx)  && (s_aliveRx  != lastRx)  &&
     (s_aliveBtn != lastBtn) )
{
    Wdog_Feed();
}
```

这样做的直接后果：**拔掉 CAN 线不会引起复位**。CAN 断了，五个任务照样在跑、照样自增，狗照样喂；系统只是按第 2 级超时进 FAULT，屏幕显示 `NO PEER T… R0`（自己在发、一帧没收到）或 `NO ACK`（帧被拒收），后面还跟着 T/R 错误计数器，插回线 1 秒左右自动恢复。

如果反过来把喂狗放在 `vTask_CAN_Tx` 里（G474 就是这么做的，因为它的发送是非阻塞的），一旦发送路径因为总线错误卡住，就会出现**复位循环**：复位 → 醒来还卡 → 再复位。所以"喂狗挂在哪个任务上"不是随意选择，它决定了 WDOG 管的是什么故障。

> **调试注意**：在 IDE 里下断点会让程序停住超过 1s，从而触发复位。所以单步调试前要把 `rtos.c` 顶部的 `#define WDOG_ENABLE` 改成 `0U`。**当前仓库里它就是 `0U`**——排查复位循环时关掉的，正式跑之前记得改回 `1U`。

**WDOG 换来的不是"更安全"，而是"可恢复"**：没有它，S32K 跑飞后 0x180 停发，G474 冻结，车从此不响应任何操作，且永远不会自愈；有了它，系统在 1s 内自动重启并重新发帧，而重启后"回 P"这个动作又被第 ① 条的 `g_shift_inhibit` 拦住。

## 已知风险（诚实清单）

### ① 运行中复位 → 模型回 P → 舵机拉到 P（**已加固**）

**机理**：S32K144 因 IWDG/掉电/烧录复位后，`GearShift_Stateflow_initialize()` 把状态置为 P，第一帧 0x180 发 `target_gear=0`。G474 收到后立即把舵机从 108°（D）拉到 0°（P）——**即使车在行驶**。实车上这会让 P 挡锁止爪插进转动的齿轮。

**已实施的加固（方案 C 的加强版）**：光加车速字节不够——S32K 复位后自己算出来的车速也是 0。所以真正生效的是**三条判据的组合**：

```
G474 在 0x180 接收回调里（Core/Src/fdcan.c）：
  ① 生命计数不连续（life != last+1）      → 对端可能重启过
  ② 车速单帧下跌 > 10 km/h                → 物理上不可能，只能是数据源重启
  → 只要当时「上次车速 > 5 km/h」，就锁存 g_shift_inhibit = 1

G474 舵机任务里（Core/Src/app_freertos.c）：
  g_shift_inhibit 置位时，target_gear = 0(P) 或 1(R) 一律拒绝执行，
  保持当前角度，并在 0x280 的 status bit1 上报。

S32K 侧：
  status bit1 置位 → 屏幕 t1 显示 "EXEC LOCK"
```

**锁存语义**：一旦锁存，**只有断电重启才能解除**。理由与安全气囊的碰撞锁存相同——"控制器在行驶中重启过"这件事，事后无法证明车辆已经安全，要求人工确认。

**演示方法**：踩油门到 60km/h → 按 S32K 复位键 → 看舵机**不动**、屏幕 `EXEC LOCK`。这是整个项目最能体现"功能安全思维"的一幕。

**已知代价（诚实说明）**：行驶中拔 CAN 线、等车停稳后再插回去，同样会触发锁存——因为恢复通信那一刻，执行侧无法证明"S32K 在这段失联时间里没有重启"。这是保守换安全的有意取舍。彻底解决的升级路径：S32K 用自己的 RTC 后备寄存器存"上电次数"，随帧广播；执行侧比较该计数，就能把"重启"和"丢帧"彻底分开。

### ② 舵机无位置反馈

`actual_gear` 是 G474 "我记得执行到哪"，不是从舵机读回的真实角度。舵机卡死、齿轮打滑、PWM 线断——三种故障在软件上完全不可见。

**加固**：G474 的 ADC1 已经配好 4 通道 DMA（`g_adc_buffer[4]`），只差一个反馈电位器。接上后：

```c
if (abs(g_adc_buffer[0] - target_angle_deg) > 5 && 持续 200ms) {
  g_status |= STATUS_SERVO_FAULT;
}
```

### ③ life_counter：G474 侧已用于重启检测，S32K 侧仍只发不校验

G474 的接收回调现在用它做"对端是否重启"的判据（`life != last+1`），并与车速突变判据并联使用（见 ① 的加固说明）。

S32K 侧仍然不发校验（它只接收 0x280 的状态），后果：

- 无法检测"重复帧"（CAN 控制器理论上不会重复交付，但总线错误恢复时可能有旧帧）。
- 无法检测丢帧速率（虽然超时机制覆盖了"连续丢很多帧"的情况）。

**进一步加固**：S32K 侧记录 `last_life`，每帧检查 `(life == last_life + 1) & 0xFF`；连续 3 次不符 → 计一次"通信质量下降"。

### ④ S32K 侧看门狗（**已加固**）

**代码已完成，当前处于关闭状态**：`src/sbw_wdog.c`，超时 1.0s（LPO 128kHz/256 → TOVAL 500），喂狗在 `vTask_Heartbeat`（500ms）。`rtos.c:73` 的 `WDOG_ENABLE` 现在是 `0U`（排查复位循环时关的），改回 `1U` 即启用。

**喂狗条件不是"心跳任务自己在跑"，而是"五个周期任务都在跑"**——见第 4 级。这个区别决定了它是"调度器存活检测"还是"单个任务存活检测"，前者才有意义。

**已知代价**：IDE 单步调试时会被复位，调试期把 `rtos.c` 里的 `WDOG_ENABLE` 改成 `0U`。

**尚未做的**：没有"复位原因计数"。如果某个故障导致反复复位，系统会一直重启。工业做法是把复位次数写进后备寄存器（或 RTC 后备域），十分钟内超过 N 次就进"锁定维护"态并记 DTC，而不是无限重试。

## 故障注入的演示方法（面试必备）

| 注入动作 | 预期现象 | 说明什么 |
|----------|----------|----------|
| 拔 CAN 线 | 屏幕 t1 显示 `NO PEER T… R0`（自己在发、一帧没收到），2s 后 t0 显示 `FAULT`；舵机**不动**、电机**软切到 0** 并显示 `PWR CUT` | 两级超时 + 冻结/软切双策略 |
| 拔 CAN 线后再插回 | **不复位**，1s 左右恢复（车速 ≤5 时不锁存；行驶中拔过会锁 `EXEC LOCK`，需断电） | 喂狗与 CAN 无关 + G474 bus-off 自愈 |
| 让 S32K 进 FAULT 但通信正常 | 舵机**保持原位**，串口 `Status` 的 bit2 置位 | 非法码拦截（不再自己换挡） |
| 拔舵机 PWM 线 | 屏幕档位照常切换，但执行器不动 | 说明反馈是"假的"（缺口 ②） |
| 摇杆不回中直接再推 | 不换挡 | 边沿检测 |
| 行驶中按 P 键 | 不动作，屏幕 `STOP FIRST` | `throttle_pct==0 && speed==0` 在模型里挡着 |
| 不解锁推摇杆 | 不动作，t1 显示 `NEED UNLOCK` | P 挡总闸 |
| 挡位在 P/N/R 时踩油门 | 电机**不转**，屏幕 `NO DRIVE` | 挡位门（`g_actual_gear` 判定） |
| D 挡踩油门同时踩刹车 | 电机 200ms 内降到 0，屏幕 `BRAKE CUT`，松刹车即恢复 | 刹车优先（不锁存） |
| S32K 复位（**行驶中**，车速 > 5） | 舵机**不动**，t1 显示 `EXEC LOCK`，锁存至断电 | 缺口 ① **已加固** |
| S32K 复位（**静止**） | 舵机回 P，正常工作 | 静止复位无害，不误锁 |
| 人为卡死某个任务（如 ADC 任务里写 `for(;;);`） | 约 **1s 后 S32K 硬件复位**（需先把 `WDOG_ENABLE` 改回 1） | 看门狗 + 任务活体检测 |

**面试话术**：主动说出第 1 条和最后两条。"我们做了两级通信超时 + 两颗 MCU 各自的独立看门狗；另外我补了一个执行侧的独立判据——如果决策 ECU 在车还在动的时候重启过，执行侧会锁存并拒绝任何 P/R 指令，屏幕上显示 EXEC LOCK，必须断电才能解除。因为复位后 S32K 自己报的车速也是 0，所以判据不能只看车速，得看生命计数是否连续、车速是否出现物理上不可能的阶跃。看门狗这边我特意没挂在 CAN 发送任务上——否则总线故障会变成复位循环；挂在心跳任务里、并且要求五个任务都有进展，它才真正检测'死机'而不是'断线'。"
