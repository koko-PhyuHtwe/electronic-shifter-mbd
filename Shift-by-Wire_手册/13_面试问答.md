# 第 13 章：面试问答

> 每题给出**一句话答案**（先说结论）+ **展开骨架**（按需展开）。面试时先给结论，被追问再展开。

---

## 一、架构与选型

**Q1：为什么用两颗 MCU 而不是一颗？**
一句话：**时序隔离 + 两个独立的故障判定点**。
展开：决策逻辑是状态机（Stateflow 生成码里有长分支），舵机控制是硬实时（10ms 内几十行）。拆开后任一侧改软件都不影响另一侧时序；而且任一侧挂了，另一侧能独立发现（通信超时）。

**Q2：为什么 500kbps Classic CAN 而不是 CAN FD？**
一句话：**载荷才 7 字节，Classic 够用，双向合计占用率约 4.5%**。
展开：标准帧 8 字节约 111 bit，10ms 一帧 → 单方向 2.2%。上 FD 的收益要等"全量数据广播"才有意义（P5 规划）。

**Q3：两侧采样点不一样（87.5% vs 80%），有问题吗？**
一句话：**短总线上没问题，量产必须统一**。
展开：容差内能通信，但 AUTOSAR 建议 80%±2%。统一方法：把 G474 的 TimeSeg1 调小或 S32K 的 phaseSeg2 调大。

**Q4：为什么不用 SPI 直连，非要用 CAN？**
一句话：**CAN 是车上的事实标准，且天然带仲裁、错误检测、多节点**。
展开：台架上只有两个节点看不出优势，但真实车上换挡器要和 VCU、仪表、网关通信；CAN 的差分传输抗干扰，单线故障不会拖死总线。

## 二、Stateflow 与建模

**Q5：生成码 721 行，你怎么读？**
一句话：**入口只有一个 `step()`，里面一个大 `switch`，每个 `case` 就是"当前状态 + 所有出边"**。
展开：三条规则——① 输出写在 case 最前；② 守卫按顺序排列，先命中先赢；③ `comm_timeout_timer` 在每个 case 的 `else` 里累加。

**Q6：`UnitDelay1_DSTATE` 是什么？**
一句话：**上一拍的摇杆值，用来做边沿检测**。
展开：`stick_x==1 && UnitDelay1_DSTATE==0` 意味着"摇杆刚从回中位推到前推位"。作用：按住不放不会连续触发换挡，必须先松手回中。

**Q7：为什么手动模式的 6 个挡位要建成 6 个子状态，不用一个变量？**
一句话：**每个挡位有自己的升降挡门槛，子状态让"当前几挡"成为状态本身**。
展开：`current_gear = 11U` 直接写在 case 里，代码即文档；用变量要额外维护合法性。

**Q8：改模型后怎么保证生成码和手写代码不脱节？**
一句话：**接口变更会让映射代码编译失败，这是特性不是缺陷**。
展开：`rtos.c` 里把 9 个字段逐个赋给 `GearShift_Stateflow_U`，增删端口必然编译错，强制开发者去改映射。（2026-11-06 加 `throttle_pct` 就是这么走了一遍。）

## 三、RTOS

**Q9：为什么 CANRx 任务优先级最高？**
一句话：**它只做搬运（<20µs），但它的执行节奏直接决定超时判定的准确性**。
展开：若被阻塞，`timeoutCnt` 的更新和真实帧到达节奏脱钩，500ms 判定失真。

**Q10：任务间为什么不用队列/信号量？**
一句话：**全是单写单读的 8/16 位整数，M4 上读写原子，读到上一拍的值无害**。
展开：用互斥量反而引入优先级反转。如果将来传结构体，必须改队列。

**Q11：100ms 的 Debug 任务发 8 条串口指令要 17ms，会影响 10ms 任务吗？**
一句话：**不会，它优先级最低（2），10ms 任务都是 3**。
展开：FreeRTOS 抢占式调度，Debug 发送过程中被 ADC/Gear 任务抢占，串口字节由硬件 FIFO 继续发。

**Q12：如果 HMI 发送阻塞了怎么办？**
一句话：**Nextion 是单向指令，`HMI_SendString` 里用阻塞式串口发送，最坏 17ms 占用 CPU**。
展开：这就是把它放最低优先级的原因；进一步优化可用 DMA + 环形缓冲。

## 四、ADC 与传感器

**Q13：摇杆回中值 2936，为什么不能用固定阈值？**
一句话：**因为 2936 已经超过"后拉"阈值 2800，松手就被判成推到底**。
展开：这是"不解锁也能进 D / 乱跳 M"的根因。

**Q14：自校准怎么做的？**
一句话：**上电前 100 次采样（1s）求平均作为回中基准，期间强制输出 0**。
展开：之后 `lo = rest - rest×95%`、`hi = rest + (4095-rest)×95%`。

**Q15：为什么用 95% 行程而不是 80%？**
一句话：**80% 在机械行程一半就触发，手感太"短"；95% 贴近电气尽头**。
展开：实测触发值 143 和 4041（设计值 147/4037），说明代码按设计执行。

**Q16：迟滞 120 counts 是干什么的？**
一句话：**防止推到边界附近时在 1/0 之间抖动**。
展开：`prev==2` 时把 `lo` 加 120，`prev==1` 时把 `hi` 减 120，形成"进得去、出不来"的环。

**Q17：ADC 死区为什么是 200？**
一句话：**踏板静止时读数在 30~120 之间跳动，200 能彻底滤掉**。
展开：旧值 60 导致静止时油门显示 1~2%，车辆模型里就会持续加速（"松刹车就飙车"）。

**Q18：8 点滑窗和 4 点滑窗的区别？**
一句话：**踏板用 8 点（响应慢但平），摇杆用 4 点（响应快）**。
展开：摇杆要的是"及时捕捉推拉动作"，踏板要的是"平稳的百分比"。

## 五、CAN

**Q19：0x180 和 0x280 的字节怎么分配的？**
一句话：**0x180：B0 档位、B1 显示、B2 预留、B3 生命计数、B4 车速、B5 油门、B6 刹车；0x280：B0 实际档、B1 角度、B2 状态位、B3 生命计数**。
展开：车速和刹车字节是后来加的——因为"执行侧要独立判断能不能动"就必须知道车在走多快、驾驶员踩没踩刹车。见第 5 章表格。

**Q20：为什么 `AutoRetransmission = DISABLE`？**
一句话：**控制帧宁可丢，不可旧**。
展开：总线错误时自动重传可能把过期指令送出去；关闭后丢帧由下个 10ms 的新帧顶上。

**Q21：life_counter 有什么用？现在校验了吗？**
一句话：**S32K 侧只发不校验；G474 侧已经用它做"对端是否重启"的判据**。
展开：G474 的接收回调里，`life` 不连续**且**当时车速为 0 → 怀疑重启；配合"车速单帧下跌 >10km/h"这条物理不可能事件，一起锁存。S32K 侧仍可加 `(life == last+1) & 0xFF` 连续 3 次不符计异常——这是 P4 的收尾项。

**Q22：CAN 收不到数据怎么排查？**
一句话：**先示波器/万用表，再读代码**。
展开：量 CANH/CANL 差分（显性 ~2V）、断电量终端电阻（60Ω）、确认 `HAL_FDCAN_Start()` 被调用、检查过滤器 mask。

**Q23：为什么用队列接收而不是中断里直接解析？**
一句话：**中断只搬运，业务在任务里做**。
展开：拉长中断会恶化响应；16 槽队列 = 160ms 缓冲，吸收任务抖动。

## 六、故障安全

**Q24：通信断了会发生什么？**
一句话：**G474 500ms 后冻结舵机（不归位），S32K 2s 后进 FAULT**。
展开：**冻结是刻意的**——行驶中把 D 拉到 P 会打坏机构。

**Q25：为什么不设计成"超时就回 N/P"？**
一句话：**故障时的可恢复性优先于"看起来安全"的动作**。
展开：高速行驶中失去动力（回 N）会被追尾；强制进 P 会打齿。

**Q26：FAULT 状态怎么退出？**
一句话：**只能人工确认：按 P 键 + 踩刹车 + 停车 + 摇杆回中**。
展开：模型 v1.22 起条件写进生成码——`p_button && brake_pedal>30 && speed<5 && x_prev==0`。屏幕会逐条告诉你卡在哪：`FAULT: NO LINK` / `PRESS P` / `STOP CAR` / `CENTER`。

**Q27：IWDG 1.25s 怎么算的？**
一句话：**LSI 32kHz / 64 = 500Hz，reload 625 → 1.25s**。
展开：喂狗放在 CAN 发送任务里，与"能发出帧"绑定；它只管"CPU 卡死后把通信恢复起来"，舵机力矩本来由 TIM3 硬件维持，所以不需要给它很长的容忍。

**Q28：这个系统最大的安全缺陷是什么？**
一句话：**现在最大的缺口是舵机没有位置反馈；"行驶中复位"这个高危项已经堵掉了**。
展开：0x180 加了车速字节，G474 用两条判据识别对端重启——生命计数不连续、车速单帧下跌超过 10km/h（物理上不可能）——只要当时车速 >5，就锁存拒绝 P/R 指令，屏幕显示 `EXEC LOCK`，必须断电解除。为什么不只在 S32K 拦：因为出问题的就是 S32K 自己，它复位后报的车速也是 0。

**Q29：舵机卡死能发现吗？**
一句话：**目前不能，因为没有位置反馈**。
展开：`actual_gear` 是"我记得执行到哪"，不是真实角度。G474 的 ADC1 已配好 4 通道 DMA，接上反馈电位器就能闭环。

## 七、调试经历

**Q30：讲一个你调了很久的 bug。**
一句话：**摇杆必须斜着推才响应，最后发现是电位器 GND 悬空**。
展开：现象诡异地像软件问题（通道配置、滑窗长度都查了），本质是模拟量没有参考地，只有两轴成回路才拉得出电流。教训：**模拟量异常先量电源和地**。

**Q31：有没有"改了半天发现是没烧录"的经历？**
一句话：**有，P 键那次**。
展开：改完极性编译通过，现象没变，最后确认板子里跑的还是旧固件。教训：启动时打印版本号。

**Q32：你怎么确认修好了而不是"看起来好了"？**
一句话：**把中间量打到屏幕上，看它是不是按设计变化**。
展开：比如摇杆触发值 143/4041 与设计值 147/4037 吻合，证明"代码按设计执行"，剩下的差异是硬件。

## 八、项目与团队

**Q33：这个项目你独立完成还是团队？**
一句话：按实际回答，重点讲**你负责的那部分的技术决策**。（不要夸大全包，会被追问细节暴露。）

**Q34：如果让你重做，会怎么改？**
一句话：**先加位置反馈和执行侧车速门，再谈建模**。
展开：功能安全的优先级是"闭环 > 互锁 > 看门狗"。

**Q35：这个项目最难的地方？**
一句话：**不是写代码，是"证明代码真的在跑"**。
展开：没有调试器、没有逻辑分析仪时，靠串口屏把中间量暴露出来，是最有效的定位手段。

**Q36：下一步计划？**
一句话：**先开看门狗、补 life 校验，再加速度门和位置反馈，最后 P5 CAN FD**。
展开：当前 `WDOG_ENABLE` 还是 0（为排查复位循环临时关的），软切 A/B/C 测试也还没跑完——这两项是收尾；位置反馈和三相闭环是下一阶段。

## 答题心法

| 原则 | 说明 |
|------|------|
| 先结论后展开 | 面试官时间有限，第一句话决定他是否追问 |
| 用数字说话 | "回中 2936""2s 超时""1.25s 看门狗"比"比较久"有说服力 |
| 主动暴露缺陷 | "这里有个已知问题，加固方案是 X"比"都做完了"可信 |
| 不说"应该" | 不确定就说"实测是 X，理论上限是 Y" |
| 能指到行号 | "在 `GearShift_Stateflow.c:451` 的 D 状态里"比"在那个文件里"强十倍 |
