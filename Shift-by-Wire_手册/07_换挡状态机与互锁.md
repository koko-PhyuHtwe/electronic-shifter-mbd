# 第 7 章：换挡状态机与互锁逻辑

## 为什么需要互锁

换挡执行器是一根带电机的旋转轴，P/R/N/D 四个位置对应 0°/36°/72°/108°。如果在车速 80km/h 时把轴从 D 转到 P，**驻车棘爪会撞进高速旋转的输出轴**——轻则打齿，重则抱死。

所以每一个"从静止挡位离开"的动作都必须是**有条件的**：人要有意识（按解锁键）、车要停住（车速 < 5km/h）、脚要踩刹车（防止溜车）。这就是互锁。

## 全部过渡一览（生成码里的真实条件）

| 过渡 | 条件（AND 关系） | 设计意图 |
|------|------------------|----------|
| **P→D** | `stick_x==1` 且 `brake>30` 且 `speed<5` 且 `unlock` 且 `x_prev==0` | 四重条件：前推摇杆表意图、踩刹车防溜车、停车、解锁键表"我现在要换挡" |
| **P→R** | `stick_x==2` 且 `brake>30` 且 `speed<5` 且 `unlock` 且 `x_prev==0` | 同上，方向相反 |
| **R→N** | `stick_x==1` 且 `speed<5` | 退出倒挡只需停车 + 前推 |
| **R→P** | `p_button` 且 `brake>30` 且 `speed<5` | 按 P 键回驻车（**模型 v1.24 起刹车条件已写进模型**） |
| **N→D** | `stick_x==1` 且 `x_prev==0` | 空挡进前进挡，无需解锁（见下文） |
| **N→R** | `stick_x==2` 且 `speed<5` 且 `x_prev==0` | 倒挡必须停车 |
| **N→P** | `p_button` 且 `brake>30` 且 `speed<5` | 同上 |
| **D→N** | `stick_x==2` 且 `x_prev==0` | 后拉回空挡 |
| **D→P** | `p_button` 且 `brake>30` 且 `speed<5` | 同上 |
| **D→M** | `stick_y==2` 且 `x_prev==0` | 右推进手动 |
| **M→D** | `stick_y==1` | 左推回自动 |
| **M→P** | `p_button` 且 `brake>30` 且 `speed<5` | 同上 |
| **任意→FAULT** | `valid==0` 持续 `comm_timeout_timer > 200`（200 步 × 10ms = 2s） | 通信失效 2s |
| **FAULT→P** | `p_button` 且 `brake>30` 且 `speed<5` 且 `x_prev==0` | 故障确认：按 P + 踩刹车 + 停稳 + 摇杆回中 |

> **为什么 `→P` 是三重条件**：按 P 键表意图、踩刹车防溜车、车速 < 5 确保停稳。少任何一条都可能让驻车棘爪在轮子还在转的时候咬上去。
>
> **"车在动就挂 P" 这条规则在模型里（v1.24 起）**：D→P 和 M→P 的条件末尾还多了
> `throttle_pct == 0 && vehicle_speed == 0`，也就是"踩着油门、或者车还在走"时按 P 一律无效。
>
> 这条规则原来写在 `rtos.c` 里（输入侧把 `p_button` 屏蔽掉），2026-11-06 加了这个输入端口后
> 正式搬回模型。**搬回去的理由**：规则写在模型里，读模型的人一眼能看见，仿真时也能验证；
> 写在代码里则等于"模型之外还有一条没人知道的规则"，迟早分叉。
>
> 搬回后 `rtos.c` 只做纯映射，不再二次屏蔽——**一条规则只留一个出处**。
> 执行侧的独立拦截仍然保留（`app_freertos.c` 里 `g_vehicle_speed > 5` 就拒绝任何 P/R 指令、
> `g_brake_pct < 30` 就拒绝 P），那是另一层，不依赖 S32K 判断是否正确。
> `x_prev` 就是生成码里的 `UnitDelay1_DSTATE`，保存上一步的 `stick_x`。`x_prev==0` 意味着**摇杆必须处于回中位置**——这是"一次一动作"的关键。

## 为什么 D/N/R 之间不需要解锁键？

这是一个被认真讨论过的设计问题。

**反方观点**：不解锁就能从 D 到 N，那不就能在行驶中乱切？

**正方（最终采纳）**：因为**上电必进 P**。

```c
/* GearShift_Stateflow.c 初始化 */
GearShift_Stateflow_DW.is_active_c3_GearShift_Stateflo = 1U;
GearShift_Stateflow_DW.is_c3_GearShift_Stateflow = GearShift_Stateflow_IN_P;
```

系统第一次执行时无条件进 P，而 P→D / P→R 要求 `brake>30 && speed<5 && unlock`。也就是说，**解锁键是整台车的总闸**：不解锁，你连 D 都进不去，那 D/N/R 之间的切换自然不会造成危险。

这和真车一致：BMW 的电子挡把在 D 与 N 之间可以自由切换（等红灯挂 N），但要从 P 出来必须踩刹车按解锁。

> 补充：早期版本曾把"D/N/R 无互锁"当成缺陷（记为"洞 2"）。核查模型初始化后**该判断被撤销**——不是缺陷，是设计。

## 五个必须理解的细节

### ① 边沿检测：按住不放不会连跳

```
if (stick_x==1 && UnitDelay1_DSTATE==0)  → 允许切换
末尾：UnitDelay1_DSTATE = U.stick_x;
```

如果摇杆一直保持前推，第一拍 `x_prev==0` 命中过渡，第二拍 `x_prev==1` 就不再命中。**想再换一次，必须先把摇杆松回中位。** 这消除了"推到底一直按住 → 状态机以 10ms 频率疯狂跳转"的风险。

### ② `brake>30` 而不是 `brake>0`

踩刹车时 ADC 有个爬升过程，且有噪声。30% 是"明确踩下"的阈值，能过滤"脚轻搭在踏板上"的情况。

### ③ `speed<5` 而不是 `speed==0`

车速是浮点积分出来的，永远有残差。用 `==0` 会让车"永远停不下来"。5km/h 是行业惯例（泊车棘爪允许的极限啮合速度）。

### ④ M 模式入口按车速自动选挡

```
IN_Init: speed <10 → M1, 10~30 → M2, 30~50 → M3, 50~70 → M4, 70~90 → M5, ≥90 → M6
```

从 D（自动挡，随时在合适齿比）切到 M 时，必须给一个"合理的起始挡位"，否则会出现"80km/h 挂在 M1"的荒谬状态。

### ⑤ M 内的升降挡是"双通道"

```
升挡：rpm > 6500                     ← 保护性自动升挡（防止超转）
      或 stick_x==2 && rpm>=2000 && speed>=25/50/80/120/160  ← 手动请求
降挡：rpm < 1200                     ← 保护性自动降挡（防止拖挡熄火）
      或 stick_x==1 && speed<=15/40/70/100/140               ← 手动请求
```

两条通道**并列**而不是互斥：即使驾驶员不操作，转速过高/过低也会自动挡位保护。这是"手动模式"而非"纯手动"——真车的 M 模式同样有断油保护。

## 状态机的一个隐蔽性质：时间不是连续的

生成码每个状态体里都有：

```c
} else if (valid) { comm_timeout_timer = 0U; }
else { comm_timeout_timer++; }
```

注意它是 `else if` ——**只要有任何一条出边命中，计数器就不清零也不累加**。这意味着：在持续换挡的极端场景下（10ms 一跳），`comm_timeout_timer` 可能停滞。这是一个理论上的边界情况（实际不可能每 10ms 换一次挡），但如果要做严格的形式化验证，应把计时器移到状态机之外，独立于状态转移计时。

## 三个可以改进的点

| 问题 | 现状 | 建议 |
|------|------|------|
| 无 P→N 直接通路 | 只能 P→D→N 或 P→R→N | 真车允许 P→N（拖车模式），可加一条 `stick_x==1 && brake>30 && speed<5 && unlock` 且**不改变齿比**的过渡 |
| M 内没有 N 出口 | M 只能回 D 或 P | 加 `stick_y==1` 长按 → N |
| 摇杆方向与真车相反？ | 前推=D，后拉=R | 需确认与物理挡把方向一致（本项目摇杆是游戏杆，非挡把） |
