# 第 11 章：调试踩坑记录（14 个真实故障）

> 这一章是整本手册最有价值的部分。每个坑都写清**现象 → 误判 → 真因 → 修法**。
> 面试时讲这里的故事，比讲架构更能证明你真的调过板子。

---

## 坑 #1：上电就是 R 挡

**现象**：上电后舵机停在 R 位（36°），屏幕显示 P，但执行器不在 P。

**初判**：以为 Stateflow 初始状态写错了。

**排查**：模型初始化确实是 `is_c3_GearShift_Stateflow = IN_P`，`current_gear` 也输出 0。问题在 G474 侧：

```c
static uint8_t last_gear = 0;   /* ← 罪魁 */
if (g_target_gear != last_gear) { 更新舵机 }
```

`last_gear` 初值 0（P），第一帧 `target_gear` 也是 0（P） → **条件永远不成立 → 舵机从来没被初始化**，停在上电时的默认 PWM（≈1.5ms，90°，看着像 R）。

**修法**：`last_gear = 0xFFU`，保证第一帧必进更新分支。同时在 `MX_TIM3_Init` 之后主动写一次 P 的角度。

**教训**：**"值相等"不等于"已经同步过"**。任何"变化才动作"的逻辑，初值必须是一个不可能等于真实值的哨兵值。

## 坑 #2：刹车一松，车速拼命往上冲

**现象**：车辆模型里只要不踩刹车，车速一路飙到 240。

**初判**：以为积分公式符号错了。

**排查**：把油门 ADC 原始值打到屏幕上 —— **静止时读到 2.0V 左右（约 50%）**。原因有两个：

1. 踏板电位器没校准，静止时本来就输出一个中间值。
2. 死区设成 `ADC_DEAD_LOW = 60`，只滤掉 1.5%，50% 全被当成真实油门。

**修法**：死区提到 **200**（约 5%），并在 `ADC_RawToPercent()` 里做 `(raw - DEAD_LOW) * 100 / (4095 - DEAD_LOW)` 的线性映射，而不是简单的 `raw * 100 / 4095`。

**教训**：**"静止时 ADC 读数不是 0"是所有模拟量输入的第一课**。死区不是可选项，是必需品。

## 坑 #3：不用解锁就能进 D，还会乱跳 M

**现象**：上电后不按解锁、不踩刹车，前推摇杆就能进 D；摇杆松手时档位乱跳到 M。

**排查**：把摇杆原始值和判定结果打到屏幕：**回中时 x = 2936，判定结果 = 2（后拉）**。

当时 `ADC_ToStickPos()` 用的是固定阈值：

```c
if (adc < 1200) return 1;
if (adc > 2800) return 2;   /* 2936 > 2800 → 松手就是"后拉" */
```

**这个摇杆的机械中位对应 2936，不是 2048。** 固定阈值把"松手"永久判定为"后拉"。

**修法**：放弃固定阈值，改成**上电自校准**（前 100 次采样求平均作为基准）+ **按行程百分比触发**（`rest ± 95%`）。

```c
uint16_t lo = rest - (uint32_t)rest * 95 / 100;        /* 2936 → 147 */
uint16_t hi = rest + (uint32_t)(4095 - rest) * 95 / 100; /* 2936 → 4037 */
```

**教训**：**任何电位器类输入都必须自校准**。器件公差、连杆装配角度、电源电压都会让"理论中点"失效。

## 坑 #4：摇杆必须斜着推才有反应

**现象**：单推 X 轴或 Y 轴，屏幕数字纹丝不动；**同时对角度斜推**才正常。

**初判**：严重怀疑 ADC 通道配置错了（查了三遍 `peripherals_adc_config_1.c`，EXT2/EXT3/EXT10/EXT11 全对）、怀疑扫通道时序、怀疑滑窗长度。

**真因**：**摇杆电位器的 GND 线没接**。

电位器只有 VCC 和信号线接上时，滑臂电压是"悬空"的——只有两轴同时构成回路（通过另一轴的电位器接地）才拉得出电流，ADC 才读得到变化。

**修法**：接上 GND。用户回了一句"没有问题了,没接地"。

**教训**：**模拟量异常的第一步是量电源和地，不是读代码。** 我在软件里找了两天，硬件上是一根线。

> 附带后果：因为"必须斜推才有反应"的诡异现象，我一度得出"电位器被过驱动、机械行程只走一半就到电气尽头"的结论，还建议了加限位/改连杆比/换电位器等硬件改动。**接地修好后这个结论作废**——量程其实是完整的。这是本手册里唯一一条被推翻的结论，保留在案以示警惕。

## 坑 #5：解锁键松手时一直被判定为"按下"

**现象**：屏幕 `n5` 恒为 1（按下状态），不碰任何键也进不了正常流程。

**排查**：`pin_mux.c` 里 PTB2 配的是 `PORT_INTERNAL_PULL_UP_ENABLED`。用万用表量 PTB2 对 GND：

- 松开：**0.76 V**
- 按下：3.3 V

0.76V 低于芯片 VIL（≈0.99V）但**余量只有 0.23V**。0.76V 是"按键接 3.3V + 板上 10k 外部下拉"与"片内 30k 上拉"分压的结果。

**修法（两步）**：

1. **硬件配置**：`pin_mux.c` 里 PTB2 的 `.pullConfig` 改成 `PORT_INTERNAL_PULL_DOWN_ENABLED`，把静态电平压到 ~0V，噪声余量从 0.23V 提到 1V 以上。
2. **软件极性**：`BTN_UNLOCK_ACTIVE_LEVEL = 1U`（高有效）。

**教训**：**"配置了上拉"不等于"电平正确"**。外部电路会与片内上下拉分压。判断极性要靠万用表实测，不能靠"通常按键都是低有效"。

## 坑 #6：P 键没反应 / 一松手就回 P

**现象（用户描述）**：上电要一直按解锁才能换挡；X 前推后拉没有 N 档；回中就是 P 档；P 键没用。

**排查**：先怀疑 `p_button` 恒真——因为 D→P、N→P、R→P 的条件都是 `p_button && speed<5 && x_prev==0`，如果 P 键一直判按下，**一松摇杆就跳回 P**，完美解释全部四个现象。

改了极性（`BTN_P_ACTIVE_LEVEL = 0U`），用户回"不行"。

再让用户量 PTB4：**松开 3.3V、按下 0V** → 低有效，配置是对的，但现象还在。

**真因**：**用户没有重新烧录**。改完头文件后只是编译了，板子里还是旧固件。用户自己回了一句"ok那应该是我忘记了"。

**教训**：**每一次"改了没效果"，先确认"是不是真的跑的是新代码"**。可以在启动时往屏幕打一个版本号或让某个 LED 闪特定次数。

## 坑 #7：编译报 `board/pin_mux.h: No such file or directory`

**现象**：

```
../src/rtos.c:21:27: fatal error: board/pin_mux.h: No such file or directory
```

**真因**：NXP 配置工具生成的 `board/sdk_project_config.h` 里**已经** `#include "pin_mux.h"`，而 include 路径只加到 `board/`，不是工程根。再写 `#include "board/pin_mux.h"` 就找不到。

**修法**：删掉 `#include "board/pin_mux.h"`，靠 `sdk_project_config.h` 的传递包含。

**教训**：NXP 生成工程里，**先看 `sdk_project_config.h` 已经包含了什么**，不要重复包含。

## 坑 #8：CAN 只能收到 0x180，"收不到反馈"

**现象**：用户报"只能收到 180h 的数据"。

**排查**（两侧全查了一遍）：

- S32K 侧 `sbw_can.c`：TX MB0 = 0x180、RX MB1 过滤 0x280，配置正确。
- G474 侧 `fdcan.c`：RX 过滤器 `FilterID1 = 0x180`、mask 0x7FF、FIFO0 中断使能，正确。
- 位时序：G474 80MHz/8 = 10MHz，20 Tq → 500kbps，正确。

配置层面找不到问题。用户后来说"没有问题了/好了"——大概率是接线或屏幕显示的问题。

**教训**：**CAN 通不了时，先确认"两侧都在跑"**。用示波器看 CANH/CANL 有没有帧、量终端电阻（断电量应为 60Ω），比读代码快十倍。代码层面则优先查：`HAL_FDCAN_Start()` 有没有调、过滤器 mask 是不是过严。

## 坑 #9：屏幕收到指令但不刷新

**现象**：串口有波形，屏幕没反应。

**真因**：Nextion 指令必须以 **`0xFF 0xFF 0xFF`** 结尾，少了不执行。

**修法**：`HMI_SendString` / `HMI_SendNumber` 末尾统一补三个 0xFF。

**教训**：协议类问题先看**帧尾**。

---

## 坑 #10：我讲错了故障行为（"舵机回安全位"）

**错误说法**：我在演示话术里说"通信断了，舵机会回到安全位"。

**核查后的事实**：

```c
if (now - g_can_rx_tick > CAN_RX_TIMEOUT_MS) {
  g_status |= STATUS_COMM_TIMEOUT;   /* 只置标志 */
}
/* 没有任何 __HAL_TIM_SET_COMPARE 调用 → 角度保持不变 */
```

**G474 超时后的动作是"冻结"，不是"归位"。** 这是刻意的安全设计（行驶中把 D 拉到 P 会打坏机构），但我一开始说反了。

**教训**：**演示话术里的每一句"系统会做 X"，都要能在代码里指到那一行。** 指不到就别说。

---

## 坑 #11：控件编号全部返工两次

**第一次**：设计了 t3~t12 十个控件 → 用户说"重做吧,现在只用了一个 t0 返回"。
**第二次**：改成 t1~t10 → 用户说"不对是 b0"（**b0 是返回按钮**，代码里零引用，占了编号）。
**第三次**：挪到 t0~t9 → 用户说"放不了这么多"。
**最终**：只保留 `t0`（大档位）+ `t1`（事件），`t2` 提示行默认关闭。

**教训**：**先确认屏幕上"已经有哪些控件、哪些被占用"，再设计编号。** 不要假设屏幕资源无限。另外，HMI 工程文件是私有二进制且被 IDE 独占锁定，**外部程序无法离线编辑**，所有控件必须手工在 IDE 里加。

## 坑 #12：车速和挡位完全不可控

**现象**："车速和转速以及手动档位一点都不好控制。"

**真因**：不是 bug，是标定问题。摇杆是数字量，一脚油门瞬间 100%，0→25km/h 只要 1 秒，M1→M2 的门槛一闪而过。

**修法**（见第 9 章）：

```c
#define THROTTLE_RAMP_PER_S 0.9f   /* 满油门 1.1s */
#define DEMO_INERTIA_SCALE  3.0f   /* 等效质量 4200kg */
```

**教训**：**仿真模型也要做"人机工程"标定**。真实感 ≠ 物理正确，演示需要的是"可演示、可操作"，不是"最快"。

## 坑 #13：CANH / CANL 接反 —— 两侧同时"错误被动"

**现象**：拆装过一次接线之后，两块板同时上电就再也通不上。屏幕 t1 显示 `CAN BUS ERR`（错误被动），串口监视器里 G474 还在正常打印 `Target:...`，但它板上的 RX 指示灯**一次都不闪**。

**误判（我的）**：先怀疑软件——上电时间差导致 S32K 往无人应答的总线发帧、TEC 涨到 256 掉进 bus-off 且回不来。为此还写了"每 500 ms 重新初始化一次"的自愈代码。

**推翻误判的关键事实**：FlexCAN 的 `CTRL1[BOFFREC]` 默认就是 0（自动恢复），掉进 bus-off 后硬件等 128×11 个隐性位就会自己回到总线并清零 TEC。所以"永久狗带"的假设站不住——它只是在 320 ms 一个周期的循环里，真正处于 bus-off 的时间只有约 1.4 ms（0.4%），屏幕上自然几乎永远看到错误被动而不是 BUSOFF。

**定位方法（不靠示波器）**：把 FlexCAN ESP1 的信息全打出来：

| 屏幕 t1 | 含义 |
|---|---|
| `NO ACK T128 R0` | 我方位能正确回读 → 本板收发器与引脚都正常，帧确实上了总线，**只是没人应答** |
| `TX BITER T…` | 我方位的回读与发送不一致 → 本板收发器/引脚坏了 |
| `FORM ERR T… R…` | 双方都在发但都解不出帧 → 波特率、终端电阻、干扰 |

再加上错误计数器（`T` = ESR1[23:16] TEC，`R` = ESR1[31:24] REC），"谁的问题"一眼可分。本例读到的是 **T 在 128~255 之间、R 恒为 0**。

**真因**：**CANH 与 CANL 接反了**。接反时两个收发器都在驱动总线，但各自看到的都是反相电平，于是谁也解不出帧、谁也不给 ACK；S32K 侧表现为"发了没人理"（错误被动），G474 侧表现为"一帧都收不到"（指示灯不闪）。**两侧症状完全自洽，却和"对端没上电"一模一样。**

**修法**：把两根线对调。

**教训**：
1. **60 Ω 终端电阻只能证明"线通、电阻在"，不能证明收发器在工作。** 断电量到的 60 Ω 是无源测量，收发器没供电时它照样是 60 Ω。
2. **CAN 排障先做"对调一次"这个无损试验**：两根线对调不会损坏任何东西，接反本来就已经在错误状态了。
3. **能自动恢复的故障，不要写自愈代码**：给 bus-off 加"定时重新初始化"不仅多余，还会在发送任务并发访问时拆掉驱动状态，把可恢复故障变成永久故障。

## 坑 #14：拔掉 CAN 线再插回，通信再也回不来 —— FDCAN 的 bus-off 不会自愈

**现象**：正常换挡途中把 CAN 线拔掉（为了演示"通信中断"），插回去之后**再也通不上**：
- S32K 屏幕 `t1` 显示 `NO PEER T36 R0`（或 `SILENT T36 R0`）——它在发，但没人应答，且一帧都收不到
- G474 串口**一直正常打印** `Target:...`，说明 CPU 活着、任务在跑
- 但 G474 板上的绿灯**一次都不闪**（该灯只在收到 0x180 时翻转）
- **一断电重启就立刻恢复正常**

**误判（我的）**：先后怀疑 ① 拔插时 CANH/CANL 又接反了 ② 装电机时电调 BEC 的 5V 并到了板子 5V 上导致掉电复位。都不是——用户明确"电机根本没驱动，什么都没操作就这样了"，而且"复位后又可以通信"。

**真因**：**STM32G4 的 FDCAN 进 bus-off 之后不会自己退出。**

拔线那一刻，G474 每 10 ms 发一帧 0x280 却收不到 ACK，TEC 每帧 +8，约 320 ms 涨到 256 → 硬件进入 bus-off 并把 `CCCR.INIT` 置 1，收发全部停摆。而 STM32 的 FDCAN **不像 FlexCAN 那样自动恢复**：必须软件重新 `HAL_FDCAN_Start()` 才能清掉 INIT。原代码只激活了 `FDCAN_IT_RX_FIFO0_NEW_MESSAGE`，从没处理过 `FDCAN_IT_BUS_OFF`，于是外设就永久停在 bus-off 里——只有整板复位才能救。

这也解释了"为什么 S32K 侧看起来一切正常"：S32K 用的是 FlexCAN，`CTRL1[BOFFREC]` 默认允许自动恢复，它自己从 bus-off 里爬出来了，继续发帧（TEC 又慢慢涨），所以屏幕给的是"我在发、没人理"。

**修法**（`Core/Src/fdcan.c`）：
1. 初始化时把 bus-off 通知一起打开：
   ```c
   HAL_FDCAN_ActivateNotification(&hfdcan2,
                                  FDCAN_IT_RX_FIFO0_NEW_MESSAGE | FDCAN_IT_BUS_OFF, 0);
   ```
2. 实现错误状态回调，进 bus-off 就重启外设：
   ```c
   void HAL_FDCAN_ErrorStatusCallback(FDCAN_HandleTypeDef *hfdcan, uint32_t ErrorStatusITs)
   {
     if ((ErrorStatusITs & FDCAN_IT_BUS_OFF) != 0U)
     {
       g_can_busoff_cnt++;
       (void)HAL_FDCAN_Stop(hfdcan);          /* 置 INIT */
       (void)HAL_FDCAN_Start(hfdcan);         /* 清 INIT，硬件随后自动从 bus-off 恢复 */
       (void)HAL_FDCAN_ActivateNotification(hfdcan,
              FDCAN_IT_RX_FIFO0_NEW_MESSAGE | FDCAN_IT_BUS_OFF, 0);
     }
   }
   ```
3. 串口打印加 `BO:` 字段（bus-off 自愈次数），拔插一次就 +1，用来确认自愈真的发生了。

**教训**：
1. **同一个协议，两家的错误恢复策略可能完全相反。** FlexCAN 默认自动恢复，FDCAN 必须软件重启——移植代码时这种"默认行为"差异最容易被忽略。
2. **"复位就好了"是一个强指向性的线索**：说明有状态被锁存在硬件寄存器里，而不是软件变量（软件变量复位也会清，但它同时意味着逻辑问题）。看到"只有复位能救"，先查外设的锁存型故障状态。
3. **可见性要设计进去**：给总线故障加一个自愈计数器（`BO:`），比事后猜"它到底恢复没恢复"省事得多。
