# 第 10 章：HMI 界面与演示脚本

## 串口屏的两个约束

1. **工程文件是私有二进制**：`Projcet.HMI` 约 14.5MB，被 USART HMI IDE 以 `FileShare.None` 独占打开，外部程序连读都读不了。**所有界面修改必须在 IDE 里手工做**，代码只能"发指令"，不能"生成界面"。
2. **控件数量有限**：屏幕上已有的控件就是全部可用资源，新增控件需要重新烧录屏幕工程。

这两条约束决定了软件侧的策略：**尽量复用屏幕上已有的数字控件，只新增最少的文本控件。**

## 最终界面布局

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│   ┌─────────┐    BRAKE   n0 %     RPM    n1              │
│   │         │    SPEED   n2 km/h   STICK X n3  Y n4       │
│   │   t0    │    UNLOCK  n5                                │
│   │   (大)  │                                            │
│   │    D    │    t1  = "NEED BRAKE"   ← 状态/原因行        │
│   └─────────┘    t2  = 提示行（可选，默认关闭）            │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## 控件表

| 控件 | 类型 | 内容 | 更新周期 |
|------|------|------|----------|
| `n0` | 数字 | 刹车百分比 0~100 | 100ms |
| `n1` | 数字 | 发动机转速 | 100ms |
| `n2` | 数字 | 车速 km/h | 100ms |
| `n3` | 数字 | 摇杆 X 状态 0/1/2 | 100ms |
| `n4` | 数字 | 摇杆 Y 状态 0/1/2 | 100ms |
| `n5` | 数字 | 按键诊断 `unlock \| (p<<1)` | 100ms |
| `t0` | 文本 | 大档位 `P`/`R`/`N`/`D`/`M1`~`M6`/`FAULT` | 变化时 |
| `t1` | 文本 | **状态行**：优先显示"为什么换不了挡"，见下表 | 变化时 |
| `t2` | 文本 | 提示行（`DEMO_SHOW_HINT 1` 时启用） | 变化时 |

**`n5` 的编码设计**：`(unlock?1:0) | (p_button?2:0)`

| n5 | 含义 |
|----|------|
| 0 | 都不按 |
| 1 | 只按解锁 |
| 2 | 只按 P |
| 3 | 都按 |

一个数字表达两个布尔量，省一个控件。这个技巧是在"控件不够用"的约束下逼出来的。

### t1 状态行：把"为什么换不了挡"显示出来

屏幕没有中文字体，所以全部用英文短句。`Demo_Reason()` 按优先级从高到低判断，命中即返回：

| t1 显示 | 触发条件 | 对应代码 |
|---------|----------|----------|
| `CAN INIT FAIL` | `CAN_Init()` 失败，`s_canInitialized == 0` | 同时绿灯常亮 |
| `TX BITER T… R0` | 500ms 没收到 0x280 且 BIT0ERR/BIT1ERR 置位 | 本板发送通道坏了：收发器没供电、TX 引脚焊点、STBY 脚 |
| `NO ACK T128 R0` | 同上但置位的是 ACKERR | 帧发出去了但没人应答，问题在对面或线序（**CANH/CANL 接反就是这个形态**） |
| `FORM ERR T… R…` | 置位的是 STFERR/FRMERR/CRCERR | 双方都能发但解不出帧：波特率不一致、终端电阻、强干扰 |
| `BUSOFF T256` | 控制器已被踢出总线 | 线路/收发器严重故障；默认自动恢复，通常一闪而过 |
| `NO PEER T36 R0` | 发过错（TEC>0）但**一帧都没收到**（REC==0） | 对端不在线：没上电、没烧录、或端口没接上 |
| `SILENT T0 R0` | 没收到帧，也没发过错 | 发送任务可能没跑 |
| `FAULT: NO LINK` | 已进 FAULT，但通信还没恢复 | 先等通信 |
| `FAULT: PRESS P` | 通信已恢复，等人工确认 | FAULT 的唯一出口 |
| `FAULT: STOP CAR` | 已按 P，但车速 ≥ 5 | 先停车 |
| `FAULT: CENTER` | 车速已降，但摇杆没回中 | 松手回中 |
| `FAULT: RECOVERING` | 四个条件都满足，正在回 P | 一瞬间，之后变 `P` |
| `EXEC LOCK` | 0x280 B2 bit1：对端在行驶中重启过，拒绝 P/R | 断电才解除 |
| `PWR CUT` | B2 bit3：动力已因失联/FAULT 被软切 | 松油门后恢复 |
| `BRAKE CUT` | B2 bit5 且**正在踩油门** | 刹车优先，松开即恢复 |
| `NO DRIVE` | B2 bit4 且**正在踩油门** | 当前挡位不给动力（P/N/R） |
| `STICK CAL` | 摇杆回中基准还没建立 | 上电 1 秒内正常；**一直挂着说明板子在反复复位** |
| `NEED UNLOCK` | 在 P 档且解锁键未按 | P→D/P→R 的第一道门 |
| `NEED BRAKE` | 解锁已按、`brake < 30`；或非 P 档按 P 键但刹车 < 30 | 第二道门 |
| `STOP FIRST` | 车速 ≥ 5（出 P / 挂 P / N↔R 都算） | 第三道门 |
| `PUSH FWD/BACK` | P 档三道门全过，等摇杆动作 | 提示可以推了 |
| `RPM LOW` | M 挡想升挡但 `rpm < 2000` | 与生成码门槛一致 |
| `SPEED LOW` | M 挡想升挡但车速未到 25/50/80/120/160 | 同上 |
| `SPEED HIGH` | M 挡想降挡但车速高于 0/15/40/70/100/140 | 同上 |
| `P>D` / `M1>M2` … | 档位刚刚变化 | 事件保持 1 秒后让位给上表 |

通信诊断那一行里的 `T` 和 `R` 是 CAN 错误计数器（ESR1[23:16] = TEC、ESR1[31:24] = REC），由 `CAN_GetErrCounters()` 读出。**`T` 涨到 128 以上就是控制器眼里的"错误被动"**，也就是屏幕早先显示 `CAN BUS ERR` 的那个状态——现在这句话被拆成了具体原因。

诊断实现见 [04_采集侧软件架构.md](./04_采集侧软件架构.md) 的 `CAN_GetBusState / CAN_GetErrCounters / CAN_GetErrFlags` 三件套；实战案例见 [11_调试踩坑记录.md](./11_调试踩坑记录.md) 坑 #13（CANH/CANL 接反）和坑 #14（FDCAN bus-off 不自愈）。

**演示价值**：在 P 档不动手时，t1 会依次提示 `NEED UNLOCK` → `NEED BRAKE` → `PUSH FWD/BACK`。面试官不需要你解释互锁，**屏幕自己在教**。

## Nextion 指令格式

### 数字控件

```c
HMI_SendNumber("n0", 45);
/* 实际发出： "n0=45" + 0xFF 0xFF 0xFF */
```

### 文本控件

```c
HMI_SendString("t0.txt", "D");
/* 实际发出： t0.txt="D" + 0xFF 0xFF 0xFF */
```

**三个 `0xFF` 是结束符，缺一不可。** 少了它屏幕收到完整字符串但不执行——这是最典型的"串口有波形但界面不动"。

### 发送优化：阴影缓存

```c
static char s_shadow[3][24];   /* 每个控件上次发出的内容 */

static void Demo_SendChanged(uint8_t widget, const char *value, uint8_t slot)
{
  if (strcmp(s_shadow[slot], value) == 0) return;   /* 没变就不发 */
  strncpy(s_shadow[slot], value, sizeof(s_shadow[slot]) - 1);
  HMI_SendString(names[widget], value);
}
```

100ms 周期 × 每条指令约 20 字节 = 200 B/s，115200 波特率下占用 1.7%。但如果每次都发、且加了波形控件，就会把串口挤满。阴影缓存让"只在变化时发"，是必须的。

## 演示面板逻辑（`Demo_Update()`）

```
每 100ms 调一次：
  1. 读当前档位 → 名字（P/R/N/D/M1~M6/FAULT）
  2. 与 s_lastGear 比较，不同 → s_event = "旧>新"，s_eventHold = 10（1 秒）
  3. reason = Demo_Reason(gear)   ← 见上面的状态行表
  4. t1 = s_eventHold>0 ? s_event : (reason ? reason : s_event)
        · 刚换完挡的 1 秒内显示事件，之后显示"当前为什么换不了"
  5. 推送 t0（大档位）、t1（状态行）
  6. 若 DEMO_SHOW_HINT==1，推送 t2（按档位给出操作提示）
```

**为什么事件只保持 1 秒**：换挡成功后档位已经变了，事件（`P>D`）的信息价值 1 秒内就耗尽；之后更有价值的是"下一步该做什么 / 为什么卡住"。若一直显示事件，界面就变成一个只报历史、不报原因的日志。

提示文案曾被完整设计（P 档显示 `EXIT: UNLOCK+BRAKE`、M 档显示 `M: BACK=UP FWD=DOWN` 等），但因为**控件不够 + 屏幕无中文字体**，最终把 `DEMO_SHOW_HINT` 设为 0 关掉。代码保留，改回 1 即可启用。

## 演示脚本（三档时长）

### 30 秒版（电梯里）

> "这是线控换挡台架。左边这颗 S32K144 跑 Stateflow 自动生成的换挡逻辑，右边 G474 驱动实体舵机，中间 CAN 500k。我现在踩刹车、按解锁、前推摇杆——看，P 变 D，舵机转到位。"

**动作**：踩刹车 → 按解锁 → 前推摇杆 → 松手（必须松手，边沿检测）。

### 3 分钟版（技术面）

1. **正常换挡**（30s）：P→D，指出 t0 变化 + 舵机动作 + 0x180 报文。
2. **互锁演示**（40s）：不按解锁直接推摇杆 → 无反应。**"解锁键是整台车的总闸，因为上电必进 P，P→D 需要四重条件。"**
3. **行驶中禁止进 P**（30s）：踩油门到 60km/h，按 P 键 → 无反应。**"`speed<5` 挡住了。"**
4. **故障注入**（40s）：拔 CAN 线 → 2s 后屏幕 `FAULT`，**但舵机不动**。**"执行侧 0.5s 就发现指令没了，它的选择是冻结而不是归位——因为行驶中把 D 拉到 P 会打坏机构。"**
5. **最后一道防线**（30s）：踩到 60km/h，按 S32K 复位键 → 舵机**不动**，屏幕 `EXEC LOCK`。**"决策 ECU 在车还动的时候重启了，它发来的 P 指令不可信。执行侧不会照做——这就是为什么这个判断必须放在执行侧。"**

### 10 分钟版（深挖）

在 3 分钟版基础上加：

- **摇杆校准**：解释为什么回中值是 2936 不是 2048，以及 `rest ± 95% 行程` 的算法。
- **代码生成**：打开 `GearShift_Stateflow.c`，指出 `UnitDelay1_DSTATE` 的边沿检测和 `comm_timeout_timer` 的位置。
- **车辆模型**：说明齿比与升挡门槛是配套标定的（25km/h 时 2958rpm）。
- **调试故事**：讲"上电即 R"（`last_gear` 初值）和"必须对角推才响应"（电位器没接地）两个坑。

## 演示台词的三个禁忌

| 别说 | 改说 |
|------|------|
| "这个功能我实现了" | "这条链路我从模型到执行器验证过" |
| "这里有点问题" | "这里有个已知缺陷，加固方案是 X"（具体） |
| "应该可以吧" | "当前实测是 X，理论上限是 Y" |

**面试官最想听的不是"你做完了"，而是"你知道哪里没做完、以及为什么"。**
